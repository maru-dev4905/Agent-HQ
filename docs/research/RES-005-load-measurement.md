# RES-005 — 저장소·실시간 처리 부하 측정 (HQ-112)

> 목적: 단일 NestJS 프로세스 + PostgreSQL + SSE(동기 Projection)로 MVP 부하를 처리할 수 있는지 측정하고(NFR-002, NFR-003), NFR 목표 수치와 ADR-0002·0003 재검토 조건에 대한 결론을 낸다.
> 상태: **Concluded** (2026-11-26, Claude Code). §7에 HQ-113 최적화 뒤 결과를 추가했다. 측정 코드: `apps/api/test/load/measure.load.ts`, 실행: `pnpm measure:load` (`pnpm infra:up` 필요, 통합 테스트 DB 사용, Gate 아님)

## 1. 측정 조건
- 기계: Apple M3, 8코어, 메모리 8 GiB. Node v26.13.1. PostgreSQL 18.7은 같은 기계의 Docker. 기본 연결 풀(pg 기본 10).
- **기계 부하**: 측정 중 다른 프로그램(가상 머신, Orca, 배경 영상 등)이 돌고 있었다. load average 시작 6.1 / 5.5, 끝 5.9 / 4.6(8코어), 남은 메모리 78 / 123 MiB. 조용한 기계에서는 더 좋게 나올 수 있다.
- API: 측정 프로세스 안에서 실행(`AppModule`). 런타임 설정은 문서 기본값으로 고정(outbox relay 200 ms, SSE 기본값; `.env`의 값은 쓰지 않음). rate limit만 측정용으로 크게 올렸다. Gap 감지·health 주기 작업은 끄고 필요한 곳에서 직접 실행했다.
- 부하: 시뮬레이터 부하 모드(`generateLoad`, 이번 Task에서 추가) — 세 시나리오를 번갈아 독립 run(평균 약 15건)으로 만들어 run마다 세션·Agent·Task·멱등 키가 다르다. 각 단계는 **정확히 정한 건수**를 보낸다. HTTP로 실제 전송(`fetch`).
- 같은 측정을 2회 반복했다(2026-11-26 05:28Z, 05:33Z). 아래 표는 "1회차 / 2회차"다. 이보다 앞선 시험 측정 4회는 측정 코드의 결함(실제 건수가 명목보다 적음, Gap 감지에 밀린 구멍 기록이 섞임, 실패 시 중단)으로 버렸다(로컬 리뷰 지적).

- 순차 요청에서 실패는 없었다(재시도 0건).
- dashboard update latency에는 HTTP와 outbox relay 주기(200 ms)가 들어 있고, 브라우저 렌더링은 빠져 있다. 동시 쓰기가 많을 때(아래 2.2의 lock 대기)는 재지 않았다.
- 처리량은 Event 하나마다 외부 ID 조회·append·Projection 조회·쓰기를 순서대로 하는 비용이 지배하는 것으로 보인다(약 3 ms/Event, 프로파일은 하지 않음).

### 2.2 같은 Workspace에 동시 500개 배치 (RSK-019)
요청마다 다른 Connection(같은 Workspace)으로 정확히 500건씩 보냈다.

| 동시 요청 | 1회차 | 2회차 |
|---|---|---|
| 2 | 200×2 (2.4 s) | 200×2 (3.0 s) |
| 5 | 200×5 (6.7 s) | 200×5 (8.4 s) |
| 10 | 200×6, **500×4** (10.2 s) | 200×6, **500×4** (10.2 s) |
| 20 | 200×8, **500×12** (13.0 s) | 200×7, **500×13** (11.5 s) |

- 실패 응답은 모두 `INTERNAL_ERROR`(500)였다. 동시 10건의 요청 시간 p95가 약 10.2 s로 트랜잭션 timeout(10 s, Workspace lock 대기 포함)과 맞아 그것으로 **추정**한다. 동시 20건은 최대 13.0 s로 10 s를 넘어, 연결 풀 대기(`maxWait` 5 s, 풀 10개) 뒤 timeout이 겹쳤을 수 있다. 실패 요청별 시간과 서버 로그를 남기지 않아 확정하지 못했다.
- 데이터는 잃지 않는다(트랜잭션 롤백, 같은 배치를 다시 보내면 멱등). 다만 지금의 시뮬레이터 `sendEvents`는 실패 시 재시도하지 않고, 재시도는 M2 Bridge가 맡을 일이다. 500은 "재시도해도 되는 오류"인지 알려 주지 않는다.

## 3. NFR 목표 수치 제안 (Proposed — 사용자 확인 후 requirements에 확정)
MVP 기준 부하: 로컬 사용자 1명, 동시 Agent 수 개~10개, Agent당 초당 수 건(RES-002: 도구 호출 1회 ≈ 2~3건). 넉넉히 **Workspace당 50 events/s**로 둔다.

| 지표 | 제안 목표 | 현재 측정 | 상태 |
|---|---|---|---|
| dashboard update latency | p95 ≤ 500 ms | p95 220~221 ms | **저부하 조건에서** 충족 |
| ingestion latency (Event 1개 요청) | p95 ≤ 100 ms | p95 30~36 ms | 충족 |
| 지속 처리량 | Workspace당 ≥ 50 events/s | 286~321 events/s(500개 배치, 순차 1연결) | 충족 |
| duplicate rate | 중복 저장 0건 | 0건 | 충족 |
| reconnect recovery | 끊긴 동안 5,000건을 2 s 이내에 누락·중복 없이 | 0.11~0.15 s | 충족 |
| 동시 full batch | 동시 5건까지 500 없음, 그 이상은 재시도 가능한 오류(503 + `Retry-After`) | HQ-112: 10건부터 500 → HQ-113 뒤: 10건 모두 성공, 20건은 200/503, 500 없음 | 충족(HQ-113) |
| Projection 전체 재생성 | 5만 건 ≤ 60 s (ADR-0002) | HQ-112: 77~81 s → HQ-113 뒤: 1.6~3.0 s | 충족(HQ-113) |

## 4. ADR 재검토 조건 결론
- **ADR-0002 (Event 중심 코어)** — "Projection 전체 재생성이 로컬 기준 1분을 넘을 때": HQ-112 측정에서는 해당했다(5만 건 77~81 s). 원인으로 추정한 Event마다의 DB 왕복을 HQ-113에서 메모리 fold + 일괄 쓰기로 바꾼 뒤 **1.6~3.0 s**가 되어(§7) **조건이 해소됐다.** 구조(Event 로그가 원천)는 그대로 유지한다.
- **ADR-0002** — "초당 Event가 단일 프로세스 처리 한계를 넘을 때": 해당하지 않는다(HQ-113 뒤 500개 배치 870~1,170 events/s, 제안 기준 50 events/s).
- **ADR-0003 (M1 기술 스택)** — "단일 프로세스·단일 DB가 목표 부하를 처리하지 못할 때": 해당하지 않는다. 동시 full batch의 500도 HQ-113에서 503(재시도 가능)으로 바뀌었다.
- 위 결론과 제안 기준(50 events/s)은 사용자 확인 대상이다(NFR-002a).

## 5. 후속 (Task·부채 갱신)
- **HQ-113 (위험도 3)**: 쓰기 경로 최적화 — Replay를 메모리 fold + 일괄 쓰기로, Ingestion 배치의 외부 ID 조회·Projection 쓰기를 묶음 처리, lock 대기 초과 시 500 대신 503 + `Retry-After`.
- **TD-008**: 정상 상태 Gap 감지는 5만 건에서 0.2 s 이하라 지금은 문제가 아니다. 장애 뒤 밀린 구멍 기록은 1,000개에 6~7 s. HQ-114는 로그가 훨씬 커질 때(예: 50만 건) 다시 재고 판단하도록 보류한다.
- **TD-005**: Replay가 Workspace lock을 약 80초 잡는다(오프라인 운영 필수).
- **RSK-019**: 동시 500개 배치 10건부터 timeout(실측).
- TD-010(SSE 전체 재전송)은 5만 건에서 1.5~2.4 s라 아직 문제 아님.

## 7. HQ-113 최적화 뒤 결과 (2026-11-26, 같은 세션 전후 비교)
변경: Replay를 메모리 fold + 일괄 쓰기로, Ingestion 배치는 외부 ID·Read Model 행을 배치 안에서 캐시하고 끝에 한 번 쓰기로, Workspace lock 대기 5 s 제한 + 바쁨(lock·연결 풀·트랜잭션 시간) 오류를 503 + `Retry-After`로(트랜잭션 안과 전역 오류 필터 모두).

- 과정에서 찾은 문제: 연결 풀이 다 찼을 때 pg-pool이 던지는 `timeout exceeded when trying to connect`가 바쁨으로 분류되지 않아 500이 났다. 트랜잭션 밖(토큰 Guard의 조회 등)에서 나는 경우도 있어서, 분류에 추가하고 전역 오류 필터에서도 503으로 바꾼다.
- 로그 크기 작업 중 Gap 감지(밀린 구멍 970개 7.6~41.6 s, 정상 상태 0.26~0.71 s)와 SSE 전체 재전송(1.5~5.9 s)은 회차 간 편차가 컸다(측정 끝 부하 12). 정상 상태 Gap 감지는 여전히 1 s 아래다.

## 6. 측정의 한계
- 한 기계·부하 있는 상태에서 2회 반복했다. 같은 세션 안에서 순차 처리량·대량 작업은 회차 간 10~20% 편차가 있다. **세션 사이 편차는 더 크다**: 버린 이전 세션(측정 코드 결함은 Replay 측정에 영향 없음)의 Replay는 154~183 s로 최종 세션(77~81 s)의 약 2배였다. 원인은 확인하지 않았다(기계 부하로 추정). 결론(60 s 초과)은 네 번 모두 같다. 그래서 HQ-113의 전후 비교는 **같은 세션에서 연달아** 잰다.
- 실제 Claude Code Bridge가 없으므로 hook 쪽 지연은 포함하지 않았다(RES-002, M2).
- dashboard update latency는 저부하에서만 쟀다. 동시 쓰기가 몰리면 lock 대기만큼 늘어난다.
- 500의 정확한 원인(트랜잭션 timeout인지 연결 풀 대기인지)은 서버 로그를 남기지 않아 확정하지 않았다.
